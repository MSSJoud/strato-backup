Overview

This document defines the architecture and implementation plan for integrating an InSAR (Interferometric Synthetic Aperture Radar) analysis module into the HarpiaMapper platform.

The module processes Sentinel-1 SAR image pairs to detect ground surface deformation (e.g., subsidence, landslides, volcanic activity). The final output is a phase-unwrapped interferogram representing ground displacement in centimeters, displayed on the platform map.

Phase Unwrapping

topsApp.xml must have unwrapping enabled for the final displacement output:

<property name="do unwrap">True</property>
<property name="unwrapper name">snaphu_mcf</property>

The unwrapped file filt_topophase.unw.vrt contains phase values in radians. plot.py must convert these to centimeters using:

displacement_cm = (phase / 4π) × λ × 100  |  λ = 0.05546 m (Sentinel-1 C-band)

Job States — stateDiagram
stateDiagram-v2 [*] --> queued : POST /jobs submitted queued --> running_step1 : worker picks up job running_step1 --> running_step2 : SAR pair found (insar.csv) running_step2 --> running_step3 : SAFE files downloaded running_step3 --> running_step4 : orbit files downloaded running_step4 --> running_step5 : XML configs generated running_step5 --> running_step6 : topsApp.py complete (unw.vrt exists) running_step6 --> done : PNGs generated + uploaded to GCS running_step1 --> failed : STAC search returns no valid pair running_step2 --> failed : Download error / auth failure running_step3 --> failed : Orbit not available running_step5 --> failed : topsApp.py error running_step6 --> failed : plot.py error done --> [*] failed --> [*]

Job Record Schema — Supabase

CREATE TABLE insar_jobs (
    id           UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id      UUID        REFERENCES auth.users(id),
    status       TEXT        NOT NULL DEFAULT 'queued',
    -- queued | running_step1..6 | done | failed
    step         INTEGER     DEFAULT 0,
    bbox         JSONB       NOT NULL,   -- [west, south, east, north]
    start_date   DATE        NOT NULL,
    end_date     DATE        NOT NULL,
    stac_pair    JSONB,                -- { first_id, second_id } once found
    result_url   TEXT,                -- GCS public URL for PNG
    error_msg    TEXT,
    workspace    TEXT,                -- local path: /jobs/{id}/
    created_at   TIMESTAMPTZ  DEFAULT now(),
    updated_at   TIMESTAMPTZ  DEFAULT now()
);

Component Breakdown

5.1 InSAR Worker Service (New)

A lightweight standalone Node.js/Express service responsible for managing the job queue, spawning Docker containers sequentially via child_process, generating XML configuration files dynamically, uploading results to GCS, and reporting status to Supabase.

⚙️
Tech stack: Node.js 20, Express, child_process, @google-cloud/storage. Each job gets an isolated workspace directory at /jobs/{jobId}/ with volumes mounted per job to avoid collisions.

The existing plot.py must be extended to:

  • 01 Also read filt_topophase.unw.vrt (unwrapped phase)
  • 02 Convert phase radians → displacement in centimeters
  • 03 Generate filt_topophase_unw.png with a diverging colormap (blue = uplift, red = subsidence)
  • 04 Include a colorbar with cm scale

Phase 1 — Local Development

PHASE 1
Goal: end-to-end pipeline running on a developer machine

Prerequisites

  • Docker Desktop installed and running
  • isce/isce2:latest image pulled from Docker Hub
  • Copernicus Dataspace account (free) with valid credentials
  • GCS bucket created for result storage (or use local filesystem for Phase 1)
  • Node.js 20+ installed

Infrastructure

  • Clone isce2-playbook into the repository at services/insar-worker/isce2-playbook/
  • Verify manual pipeline runs end-to-end (all 5 existing steps work locally)
  • Confirm unwrapping works: enable do unwrap in topsApp.xml, re-run isce2-insar step
  • Extend plot.py to generate filt_topophase_unw.png with displacement in cm

InSAR Worker Service

  • Create services/insar-worker/ Node.js project with Express
  • Implement POST /jobs — validates params, creates job directory, inserts to Supabase, starts pipeline
  • Implement GET /jobs/:id — reads status from Supabase
  • Implement job orchestrator running 6 pipeline steps sequentially via child_process.spawn()
  • Implement XML config generator (reference.xml, secondary.xml) using STAC pair IDs
  • Implement workspace isolation: each job at ./jobs/{jobId}/
  • Log stdout/stderr of each Docker step to ./jobs/{jobId}/logs/step-{n}.log
  • Phase 1: serve result PNG directly as static file (skip GCS upload)

Next.js Integration

  • Create app/(main)/api/insar/submit/route.ts
  • Create app/(main)/api/insar/status/route.ts
  • Add requestInSARAnalysis tool to lib/database/chat/tools.ts
  • Add checkInSARJobStatus tool to lib/database/chat/tools.ts
  • Register both tools in app/(main)/api/chat/route.ts
  • Add environment variable INSAR_WORKER_URL=http://localhost:3001 to .env.local

Validation

  • Full end-to-end test from chat: "Run InSAR analysis for [bbox] from Jan to Mar 2021"
  • Displacement PNG rendered on the map
  • Job status polling works correctly
  • Failed job returns a meaningful error message

Phase 2 — Production VM Deployment

PHASE 2
Goal: InSAR Worker Service running on a dedicated GCP Compute Engine VM

VM Specification

Machine type
e2-standard-4 (4 vCPU, 16 GB RAM)
OS
Ubuntu 22.04 LTS
Boot disk
100 GB SSD (SAFE files are ~4 GB each)
Additional disk
500 GB persistent disk for /jobs/ workspace
Network
Same VPC as App Engine / Cloud Run

VM Setup

  • Provision GCP Compute Engine VM with the specs above
  • Install Docker Engine + Docker Compose v2
  • Install Node.js 20 via nvm
  • Pull Docker images: isce/isce2:latest, python:3.11-bullseye, python:3.11-bookworm
  • Build stac-search and analyze-insar images on VM (or push to Artifact Registry)
  • Mount additional disk at /jobs/
  • Configure VM startup script to auto-start the Worker Service

Worker Service Deployment

  • Set up Systemd service for the Worker (auto-restart on crash)
  • Store secrets in GCP Secret Manager: COPERNICUS_USER, COPERNICUS_PASSWORD, Supabase credentials
  • Configure GCS authentication via VM service account (no key file needed)
  • Enable GCS upload in Worker: results uploaded to gs://{bucket}/insar/{jobId}/
  • Implement VM auto-start/stop logic: VM starts on job submit, stops after idle period

Networking & Security

  • Create internal-only firewall rule: only App Engine/Cloud Run IPs can reach Worker port 3001
  • Add INSAR_WORKER_URL to production environment (App Engine app.yaml or Cloud Run env vars)
  • Add VM service account to Supabase allowed IPs (if restricted)
💡
Cost Optimization: VM runs e2-standard-4 only while processing (~$0.13/hr). Implement auto-shutdown: after job completion + 15 min idle, VM stops itself. VM is started via GCP Compute API from Next.js when a job is submitted.
